# Git 交付

本用户希望修改任务完成后自动形成可追溯的 Git 交付，避免反复催促提交，也避免因提交而触发无关回归。默认允许本地提交；当前分支已有 upstream 时，将其作为默认授权的普通推送目标。用户当次指令和仓库的明确交付约束优先；已有授权无需重复确认。

## 确定任务边界

- 修改前查看仓库状态、当前分支和暂存区，区分已有修改与本任务修改。若任务已开始，利用已有记录和差异恢复边界，不把未知来源的修改归入本任务。
- 以一个能独立说明原因、结果的完整修复为提交单位；技能与项目分别位于不同仓库时，分别提交并报告结果。
- 文件不属于 Git 仓库时，完成修改和适用验证，说明无法提交；不自动创建仓库或配置远程。

## 按影响范围验证

根据实际差异和直接调用关系选择最小充分验证，并用一句话说明检查对象与本次改动的关系。读取适用的项目规定及现有命令，遵守明确要求的验证门槛。

| 改动 | 默认验证范围 |
| --- | --- |
| 文档或技能说明 | 检查内容一致性、引用路径和适用的格式/frontmatter；不启动整个项目回归 |
| Python 行为修复 | 原 Bug 的复现或已有针对性测试，以及直接受影响的调用方；语法检查不能单独证明行为已修复 |
| C 源码修改 | 受影响目标的编译与针对性功能检查，按实际条件使用单元测试、仿真或硬件验证 |
| 公共头文件、共享接口、构建或依赖配置 | 沿使用关系检查受影响目标，依据影响面扩大编译或测试范围 |

扩大验证必须有具体原因：共享依赖受影响、针对性验证暴露更广的问题，或适用规则明确要求。不得仅因准备 commit/push、追求额外保险或发现有更多测试可运行而扩大范围。

通过的验证可在相关代码、依赖和环境未变化时复用。验证已足以覆盖本次风险后，结束验证进入提交；不为提交阶段重复运行相同检查。不为低影响文字修改添加复述实现的测试。

缺少开发板、工具或其他条件时，区分“未验证”和“失败”：

- 本次修改已知导致失败：继续修复，不以完成修复的名义提交或推送。
- 无法执行必要验证：允许本地提交，提交说明与最终报告写明未验证项；暂缓推送，除非用户已明确允许这类未验证修改推送。
- 已有失败与本任务无关：有证据说明无关后，不扩展任务去修它；本次所需验证通过则继续交付，并报告已有失败。证据不足按未验证处理。

## 提交本任务修改

显式选择文件或修改片段进入暂存区，核对最终 staged diff 与任务范围一致，并对即将提交的差异执行适用的轻量格式检查（例如 `git diff --cached --check`）。避免用 `git add .` 或 `git add -A` 混入其他工作。

保留用户已有的工作区及暂存区内容。同一文件含混合改动时按片段隔离；无法可靠区分或无法保持用户暂存状态时，仅暂停提交并说明需澄清的边界，不自动 stash、丢弃或重写用户修改。

提交信息解释修复的问题与结果，遵循仓库已有风格。无本任务差异时无需空提交。提交后记录 commit ID。已有 hooks 正常执行；即使 hook 启动较广的检查，也不自动绕过或修改 hook。失败时先判断来源，不盲目重复提交。

## 推送到已授权目标

- 检查当前分支已有 upstream 和待推送提交范围。仅在待推送内容均属于本任务或已有明确授权、必要验证完成时，执行指向该 upstream 的普通 push；不要依赖可能推送多个分支的默认行为。
- upstream 缺失、处于 detached HEAD、待推送历史含未授权的其他提交，或目标与用户指令不符时，保留本地提交并询问缺失的目标或范围。不要猜测 remote、建立新远程或自动发布其他分支/tag。
- 遇到远程分叉、保护规则、权限或网络失败时，报告本地提交已完成和具体推送障碍；不 force push，不自动 pull/rebase/merge 来完成推送。网络结果不确定时先核查远程状态，避免无依据重试。
- 以推送返回结果确认是否成功；需要额外核实时，只核对目标远程引用。commit/push 成功不等于远程 CI 通过，另行报告已知 CI 状态，除非任务明确要求，否则不等待所有 CI 或扩大本地回归。

## 完成报告

简短说明改了什么、做了哪些相关验证及结果、本地 commit ID、推送目标与结果。存在未验证项、未提交内容或推送障碍时明确写出。全部交付成功后结束，不追加无关检查或新任务。
