## 总原则

排障的目标不是“试到能跑”，而是用证据区分假设并找到可解释、可复现、可防止复发的根因。先保护现场；不要一开始大量加日志或修改时序，避免把偶现问题藏起来。

回答中使用四类标签：

- **事实**：日志、寄存器、波形或可重复实验直接支持。
- **推测**：符合现象但尚未验证。
- **待验证假设**：写出验证实验和预期差异。
- **缺失信息**：只有它会改变排查路径时才向用户索取。

## 标准闭环

1. **描述现象**：发生了什么、未发生什么；避免只写“死机”“不工作”。
2. **定义预期**：正确状态、时序、数据和值域是什么。
3. **稳定复现**：频率、触发输入、温度、电源、负载、固件版本、编译优化和运行时长。
4. **画边界**：输入 → 模块状态 → 输出；列出硬件、驱动、RTOS、协议和应用边界。
5. **保存现场**：复位原因、PC/LR/SP、Fault 状态、任务/栈、关键寄存器、最近日志和版本。
6. **按概率和验证成本排序假设**：先验证能同时解释多数事实且实验成本低的假设。
7. **一次只改变一个变量**：设计能够产生不同预期结果的最小实验。
8. **缩小范围**：二分功能、替换输入/模块、禁用并发、降低速率或使用最小固件。
9. **定位根因**：根因必须解释触发条件、现场和为何过去未暴露。
10. **最小修复**：修复机制而非仅掩盖现象。
11. **回归与扩展检查**：原场景、边界、压力、故障注入和同类代码。
12. **沉淀观测能力**：加入不会改变关键时序的计数器、快照或自动化复现。

## 证据与工具

| 要回答的问题 | 优先工具或证据 |
| --- | --- |
| CPU 在哪里、为何异常 | GDB/JTAG/SWD、PC/LR/SP、调用栈、反汇编 |
| 地址属于什么符号 | Map、ELF、`addr2line`、`nm`、`objdump` |
| 内存是否被改写 | Watchpoint、内存哨兵、MPU、ASan（可用平台） |
| 中断是否发生/耗时 | 中断计数器、GPIO 打点、Trace/ETM、逻辑分析仪 |
| 总线/引脚是否正确 | 示波器、逻辑分析仪、协议解码、对端日志 |
| 任务是否阻塞/饿死 | RTOS 任务列表、运行时间统计、锁/队列状态 |
| 是否复位及复位来源 | Reset/Brown-out/Watchdog 状态与持久化启动记录 |
| 代码质量类风险 | Warning、静态分析、单元测试、边界/模糊测试 |

日志必须带版本、时间基准和关键状态。高频 ISR 中优先使用固定大小事件缓冲、计数器或 GPIO/Trace，避免格式化输出改变时序。

## Fault 与跑飞

面对 Cortex-M HardFault/BusFault/MemManage/UsageFault，按以下顺序：

1. 先确认具体 Cortex-M 型号与已启用 Fault；不要假定所有内核寄存器相同。
2. 读取并保存 Fault Status、Fault Address、HardFault Status 和系统处理器状态；按芯片/架构手册解释有效位。
3. 判断异常前使用 MSP 还是 PSP，提取硬件压入的异常栈帧；关注 stacked PC、LR、xPSR 和通用寄存器。
4. 检查 LR 中的异常返回信息以及 SP 是否位于有效、对齐、未越界的栈区。
5. 用 ELF/Map 和 `addr2line` 将 PC/LR 地址映射到源码；同时查看出错指令前后的反汇编。
6. 检查调用栈可信度；若栈被破坏，不把回溯结果当作事实。
7. 优先排查空/野指针、越界、栈溢出、非法/未对齐访问、除零、错误函数指针和返回地址破坏。
8. 使用 Watchpoint、MPU 守卫区、栈水位/哨兵和更严格编译告警验证。

不要仅用“清除 Fault 标志后继续运行”作为修复。异常恢复必须证明上下文仍可安全继续，否则应保存现场并受控复位。

## 偶现故障

- 建立事件时间线和失败前环形日志，记录触发输入、负载、温度、电压和计数器。
- 比较成功与失败样本，寻找最早分叉点，而非最后的错误日志。
- 检查竞态、未初始化、越界、栈/堆破坏、生命周期、超时、时钟/复位、电源完整性和硬件 Errata。
- 用提高频率、缩短超时、随机调度、内存填充、故障注入或长稳测试放大问题。
- 观察“加日志就消失”通常提示时序、竞态、栈空间或优化相关问题，但这仍是推测。
- 固定工具链和优化级别进行 A/B 实验；不要把 `-O0` 正常直接解释为“编译器 bug”。

## 并发与 RTOS

1. 标出共享对象、所有读写者和所处上下文（ISR/任务/核）。
2. 检查访问是否原子、是否有锁/临界区、是否存在正确的 happens-before 关系。
3. 检查 ISR 使用的 API、优先级限制、FromISR 唤醒与退出调度。
4. 检查锁顺序、递归、超时、优先级反转、饥饿和资源释放路径。
5. 检查任务栈水位、队列长度、堆分配失败和句柄生命周期。
6. 用任务运行统计、锁持有时间、事件 Trace 和受控调度复现。

`volatile` 不能修复数据竞争。根据语义选择原子操作、临界区、互斥锁、队列或所有权转移。

## DMA、Cache 与外设

### DMA/Cache

1. 明确 DMA 方向和数据所有权切换点。
2. CPU→DMA：检查 CPU 写入是否已 Clean 到主存，并在启动 DMA 前完成必要屏障。
3. DMA→CPU：DMA 完成且所有权转给 CPU 后，再 Invalidate CPU 的旧 Cache Line。
4. 检查缓冲区起止是否按 Cache Line 对齐和取整，避免误伤同一行中的其他数据。
5. 检查描述符、数据缓冲和完成标志是否分别需要一致性处理。
6. 核对平台 API、映射属性、总线可达性、地址转换和多核共享规则。

### 外设

按电源/时钟/复位 → Pinmux → 寄存器配置 → 状态机 → 中断/DMA → 驱动缓冲 → 协议对端检查。每个等待都设置合理超时并记录错误状态。用波形验证电气和时序，避免仅凭软件状态断定“硬件没发”。

## 复位、看门狗和启动

- 第一时间读取并持久化复位来源，确认读取/清除语义。
- 看门狗复位：找出最后一次喂狗者、任务心跳、最长临界区、中断风暴和系统阻塞点；不要简单增加超时时间。
- Brown-out/掉电：结合电源波形、复位脚、BOR 配置和关键写 Flash 时刻。
- 启动失败：用阶段标记确定 Boot ROM、镜像校验、启动汇编、时钟、内存、C Runtime、main 中最后成功点。
- 升级后失败：核对镜像头、版本/兼容性、签名、分区、向量表、回滚条件和掉电恢复。

## 修复与回归

修复说明至少包含：

- 根因及证据链。
- 修改如何破坏原故障机制。
- 对实时性、资源、兼容性和恢复路径的影响。
- 单元、模块、集成、压力、长稳、故障注入及旧版本兼容测试。
- 同类问题扫描范围，例如相同 API、缓冲区模式、锁顺序或寄存器访问方式。

若无法完全确定根因，明确剩余假设和风险，不把“多跑几次没复现”写成已修复。
