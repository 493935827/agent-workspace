# 固件项目总结与面试表达

## 保密先行

要求用户先脱敏。不要接收、复述或推断公司源代码、未公开芯片/寄存器、客户名称、内部文档、路线图、安全密钥、生产数据和未公开性能指标。使用“某 Cortex-M 平台”“某高速接口”“吞吐提升约 X%（如允许公开）”等泛化表达；无法公开的数字用可验证方法替代。

## 项目挖掘流程

一次聚焦一个项目，按需要询问：

1. **背景**：产品或系统要解决什么问题？约束是什么？
2. **职责**：用户本人负责和决策了什么？团队做了什么？
3. **技术目标**：正确性、性能、功耗、可靠性、交付或量产目标。
4. **难点与现象**：为什么不是普通实现？失败如何表现？
5. **分析过程**：有哪些假设、证据和排除实验？
6. **方案与权衡**：为何选择该方案，放弃了什么替代方案？
7. **实现**：关键模块、接口、状态机、工具和测试。
8. **结果**：功能、稳定性、效率或质量如何改善？
9. **验证**：如何证明不是偶然成功？
10. **复盘**：若重做会改什么，有何同类风险？

不要替用户编造职责、难点或数据。缺少量化指标时，可使用故障复现率、测试覆盖场景、运行时长、人工步骤减少、构建/测试时间等候选指标让用户核实。

## 项目叙事模板

### 简历版（3～5 行）

`在[脱敏背景/约束]下，负责[本人职责]。针对[关键问题]，通过[分析方法]定位[根因]，设计并实现[方案]，补充[测试/诊断/恢复机制]，最终[经核实的结果]。`

使用动作和结果开头，避免“参与了、学习了、熟悉了”占据主句。

### 面试版（2～3 分钟）

1. 20 秒：背景、目标和本人职责。
2. 30 秒：最难问题及影响。
3. 60～90 秒：假设、证据、根因、方案与权衡。
4. 20 秒：验证和结果。
5. 10 秒：复盘或可迁移能力。

### 深挖版

准备回答：

- 为什么选这个接口、任务模型、缓冲区或升级方案？
- 最坏情况、超时、并发、掉电和错误恢复如何处理？
- 如何证明根因？有没有替代解释？
- 测试覆盖了哪些边界和故障注入？
- 资源、实时性、兼容性和维护成本如何权衡？
- 你个人的贡献如何与团队贡献区分？

## 从任务描述提升为能力证据

| 弱表达 | 提升方向 |
| --- | --- |
| “写了 UART 驱动” | 说明中断/DMA 数据路径、缓冲策略、异常恢复和验证 |
| “修复 HardFault” | 说明现场保存、地址符号化、根因证据和回归防护 |
| “写 Python 脚本” | 说明减少的人工流程、异常/重试、测试和可复现性 |
| “做了升级功能” | 说明镜像校验、掉电一致性、回滚、兼容性和安全边界 |
| “优化性能” | 说明基线、瓶颈证据、变更、对照实验和副作用 |

## 岗位映射

最后把项目映射到 2～3 类岗位，说明证据：

- BSP/Bring-up：启动、寄存器、板级外设、跨软硬件定位。
- Linux 驱动：硬件数据路径、中断/DMA、并发、接口与调试。
- 验证/自动化：Python、测试设计、仪器、故障注入和报告。
- 安全/升级：可信启动、镜像、密钥边界、掉电恢复和回滚。
- 性能：Trace、基准、Cache/内存、吞吐/延迟和功耗权衡。

映射应基于项目实际证据，不因用户想申请某岗位而夸大。

## 质量检查

- 是否清楚区分用户与团队贡献？
- 是否包含一个真正的难点和证据链？
- 是否说明“为什么这样设计”，而非只列技术名词？
- 指标是否由用户确认且允许公开？
- 是否能承受对边界、失败路径和替代方案的追问？
- 是否删除公司和客户的敏感细节？
