# AGENTS.md — NoteReplica 开发规则（所有 Agent 必须遵守）

## 项目进度入口（导航规则）

继续项目工作时，**先读取 `progress/progress.md` 的当前快照**并与工作区实际状态核对；
仅在任务需要时按索引打开对应的 handoff 归档（检索，不要全量加载）。出现实质性进展时保持
快照最新；用户要求 handoff 时，将对话归档保存至 `progress/` 并更新索引行。

## 项目定位

NoteReplica 是对 Microsoft OneNote 的**行为复刻研究项目**（Web 版）。目标是可观察行为一致，
不是像素级抄袭，也不是只有导航的静态 Demo。应用使用独立品牌 NoteReplica，不使用 Microsoft 商标图形。

## 真实依据（最重要）

1. 原软件证据存放在 `docs/reference/`（真实截图）与官方文档摘录。每个功能规格必须注明证据来源：
   - `OBSERVED`：来自本机 OneNote 桌面版真实截图/操作（见 docs/reference/evidence.md）
   - `DOCUMENTED`：来自微软官方文档（附链接）
   - `UNVERIFIED`：尚未取得原软件证据的合理推断
2. 未观察到的行为一律标注 `UNVERIFIED`，**不得声称已与原 OneNote 完成对照验收**。
3. 本环境已知限制：OneNote COM 自动化通道被阻塞（详见 docs/gaps.md），`mcp__onenote` 工具未连接。
   视觉差分的 reference 侧只能使用真实截图，行为差分以截图 + 官方文档为依据。

## 功能状态标签

`UNKNOWN / DISCOVERED / SPECIFIED / IMPLEMENTED / VERIFIED / PARTIAL / FAILED`

- `IMPLEMENTED` 只表示代码存在。
- `VERIFIED` 只能由自动化测试或可复现的手工验证产生，测试命令必须写入 docs/test-plan.md。

## 统一命令系统（强制）

- 所有业务操作必须走 `src/domain/commands.ts`（CommandService）。
- UI 按钮、快捷键、自动化测试**禁止**绕过命令系统直接写 Dexie 或改 React 状态。
- `window.__nr.commands` 是给测试/调试用的同一命令入口，不是第二套实现。

## 数据与持久化

- 所有实体（Notebook/Section/Page/CanvasObject）使用稳定 ID，业务数据存于 Dexie/IndexedDB。
- 禁止把业务数据只放在 React 内存里。
- 禁止静默吞掉数据库错误：`useStore.run()` 将错误写入 `saveState='error'` 并弹出提示。

## 自由画布（强制约束）

- 禁止用单个全页 textarea/Markdown 编辑器冒充画布。
- 容器 = 独立定位对象（文档坐标，缩放/滚动不变）；拖拽只能从顶部抓取条发起；
  文本选区操作不得触发拖拽；高度随内容增长（与 OneNote 一致），宽度可调。
- 自动保存采用防抖（400ms）+ 静默高度同步，绝不向聚焦中的编辑器回写 HTML（保护光标/输入法）。

## 测试规则

1. 每个新功能同步添加测试：领域逻辑 → `tests/unit/`（Vitest），交互 → `tests/e2e/`（Playwright/Edge）。
2. 修复缺陷必须先复现失败，再验证"失败→通过"，并跑相关回归。
3. 不得为提高评分弱化测试：不许删除用例、放大容差、加大遮罩、硬编码截图。
4. 视觉差分基线来自 `desktop-agent-qa-starter/` 的流程：reference 截图必须来自原软件，
   不得用复刻软件截图替代。

## 质量门禁

提交前至少运行（见 scripts/run-gate.ps1）：

```powershell
npx tsc --noEmit -p tsconfig.json   # 类型检查
npx vitest run                      # 单元/集成
npx playwright test                 # E2E（使用系统 Edge）
```

### 代码静态检查（默认 code-verify）

**用户长期指令：代码开发任务的静态检查默认使用 `code-verify` skill**（Stage 1 静态审查；
Stage 2 目标验证只在用户明确授权时运行）。约定：

- 适用前提：目标目录是 git 仓库且已有 `.code-verify/config.json`；没有就先初始化
  （`git init` + 最小 config，`review_rules: generic`，static_commands 放仓库现有的
  确定性检查）再跑。
- 流程：改动完成 → `git add` 暂存 → `python <skill>/scripts/code_verify.py static
  --prepare --backend dsh`（队长编排子代理评审）或 `--backend claude-code`（无人值守）
  → 汇总 verdict。**静态审查默认 `--static-only`；绝不自动 commit/push。**
- 非 git 目录的特例（如 DSH 插件 bundle 注入补丁、pnpm 硬链接文件）：code-verify 不适用，
  退化为 `node --check` 语法门 + 注入标记校验（marker==1）+ 幂等重跑验证。
- 评审人 ≠ 实现人：静态审查由评审轨执行，实现轨不得自己给自己 PASS。

## 文件所有权约定（多 Agent 并行时）

- `src/domain/` `src/data/` — Data Agent
- `src/canvas/` `src/editor/` — Canvas Agent
- `src/ui/` `src/styles/` — UI Agent
- `tests/` `docs/` — Evaluator Agent（测试与验收报告）；Repair Agent 修复时需回归对应测试。
- `docs/batches/<批次id>/contract.md` — 架构师（批次契约 + 仲裁/修订追加节）；其余成员只读引用（见「上下文同步纪律」）。
- `docs/reference/` 中原软件截图只用于内部对照，不得进入产品构建产物。

## 标准组织架构与分工（业界流程映射，组队必用）

组队必须按业界软件工程流程建模：**需求 → 架构（契约冻结）→ 并行实现 → 并行验证 → 并行评审 → 并行修复 → 集成**。
队长是编排者（拆 DAG、派发、仲裁、汇报），**不承接实现/评审**。禁止"一个负责人从头做到尾"的串行编排——这是本节要消灭的头号效率杀手。

### 角色模板（实现轨数量随任务规模伸缩）

| 角色 | 人数 | 职责 | 任务 kind |
| --- | --- | --- | --- |
| 队长（主会话） | 1 | 编排 DAG、派发、仲裁、对外汇报；不写实现 | — |
| 需求分析 PO | 1 | 规格拆解、验收标准、证据标注（OBSERVED/DOCUMENTED/UNVERIFIED） | requirements |
| 架构师 | 1 | 模块边界、接口/数据契约**先行冻结**（落盘 `docs/batches/<批次id>/contract.md`，骨架先行）、依赖最小化 | work |
| Data 实现轨 | 1~2 | `src/domain/` `src/data/` | implementation |
| Canvas 实现轨 | 1~2 | `src/canvas/` `src/editor/` | implementation |
| UI 实现轨 | 1~2 | `src/ui/` `src/styles/` | implementation |
| 测试工程师 | 1~2 | 测试计划与用例**先行**（与实现并行），执行 verification | work / verification |
| 评审员 | 1~2 | 独立评审（≠实现者），按模块分片并行 | review |
| 集成工程师 | 1 | 合流、跑全量门禁 `scripts/run-gate.ps1`、集成报告 | integration |

调研/审查类任务按「一角度一任务一负责人」扇出。一个成员同一时刻只能持有一个未完成任务，所以**并行任务数 = 所需成员数**，不许一人多轨串行。

### 标准 DAG（扇出/扇入 + 跨片流水线）

```
requirements ─→ architecture(契约冻结) ─┬→ impl[data]   ─→ verify[data] ─→ review[data] ──┐
                                        ├→ impl[canvas] ─→ verify[canvas] ─→ review[canvas] ┼→ repair(按 finding 并行) ─→ integration
                                        ├→ impl[ui]     ─→ verify[ui] ─→ review[ui] ───┘
                                        └→ test-design（用例先行，与实现并行）
warmup[各轨]（与 requirements/architecture 同期并行预热，简报供架构师消费）
```

- **片内并行**：三条实现轨互不依赖，fan-out 后同时 ready、并行开工；彼此只依赖架构阶段冻结的契约，不互相等待。
- **并行预热**：组队即派发各轨 warmup 任务（「上下文同步纪律」第 6 条），与需求/架构同期执行——成员冷启动摄入零串行排队，9 人闲置 17 分钟的串行头部不再出现。
- **评审流水线化**：评审依赖绑定单轨（硬规则 7），各轨即完即评、与后续轨道并行，评审不新增串行阶段。
- **跨片流水线**：评审/修复进行中时，下一功能片的实现照常派发（不同所有权分区、无写冲突），用流水线消除串行等待。
- review 门自动生成的 repair + 下一轮 review 按 finding 拆分并行，不合并串行处理。

### 上下文同步纪律（成员会话互不共享记忆，上下文只经任务文本与仓库文件传递）

依据 nr-parallel-trial 实测（19 任务/96.5 分钟）：邮箱聊天式同步几乎为零（19 条消息全是单向完成报告），真正的开销是 ①每个 owner 冷启动重读同一批材料（架构师冷启动写契约 13m vs 同人热身改版 4.9m）②契约失同步后的返工（PO 裁决与契约 v1 矛盾 → 队长仲裁 + 契约 v2 + 5 个任务被迫修订重读）。硬规则：

1. **契约落盘为文件（单一事实源）**：冻结契约写入 `docs/batches/<批次id>/contract.md`（如 `b-20261103-backup-restore/contract.md`），仲裁/修订以追加节记录。任务文本只引用 `contract.md §节号` + 行号锚点，**禁止内联契约全文**；下游（含评审对照基线）一律读文件，禁止从团队状态逐字捞原文。
2. **契约两段式冻结**：先交 ≤1K 骨架（入口语义/命令名/归属表/**与 PO 裁决的逐条映射表**），队长核对映射零矛盾后才有权展开全文；任何偏离上游裁决的点必须在骨架中标注「提请仲裁」——禁止全文写完才暴露矛盾返工。
3. **同轨同人（会话保温）**：同一所有权分区的串行任务指派给**同一成员**，复用其跨任务持久的会话上下文（已验证模式：qa-1 连做 补缺测试→全量验证→flaky 修复，零重复摄入）；评审轨保持独立成员（评审人≠实现人不变）。
4. **锚点纪律**：任务描述 ≤1.5K、带 3~6 个 `文件:行` 锚点。实现/测试轨以契约锚点为准、抽查即可，**不得全量重验上游证据**（那是重复冷启动的主要来源）；评审轨不受此限——独立取证是评审的义务而非可选项。
5. **邮箱纪律**：成员不得向队长索要背景；疑问一律以「finding + 建议答案」形式提交；队长消息只做仲裁与指引，不复读背景。
6. **并行预热（warmup）**：组队即给每条实现/测试轨派发一个预热任务（kind=work、deps=[]），与需求/架构同期并行执行：AGENTS.md 与前情摄入、轨内代码勘察、产出 ≤1K 轨内简报（关键文件/结构/风险）。架构师消费各轨简报做**增量**契约——把冷启动摄入从串行尾部挪进并行头部（实测教训：架构师冷启动 12.8m 期间其余 9 名成员全部闲置）。

### 并行度硬规则（违反即为队长编排失败）

1. 实现阶段**至少 3 个互不依赖的实现任务同时 ready**，各配独立负责人。
2. 任务粒度：单任务只动 **1 个所有权分区** 且 **≤5 个文件**；超出必须拆分。
3. 依赖边只声明真实前置（契约/数据结构）；"先后偏好"不得写成依赖。
4. 契约未冻结不得 fan-out 实现轨（先接口后实现，避免返工式并行）。
5. 评审人 ≠ 实现人；队长 ≠ 实现人（用户未点名要求接管时）。
6. 集成是唯一合流点：依赖全部 review 通过后才开工，负责三腿门禁（tsc / vitest / playwright）。
7. **评审绑定单轨**：review 任务只依赖其对应实现任务与该轨验证的完成，**禁止依赖全局验证门**——各轨完成即评、与后续轨道并行，评审不形成独立等待阶段；verify 按腿拆分（单测/e2e）时按腿放行对应评审。

### 规模计算（与并发预算联动）

- 中型任务典型 **8~12 人**（3 实现轨 + 支撑角色）；夜间窗口大型任务可把热门轨扩到 ×2~3（15~20 人）。
- 按当前时间窗口校验上限（见「多智能体团队并发预算」）；不因"省额度"合并并行轨道——时间最少原则，宁并行不串行。
- 成员默认继承队长模型路由（flash）；glm-5.3 额度稀缺，仅夜间大任务的架构/评审岗按需少量混编。

### 队长建队自检清单（create 前逐项过）

- [ ] 并行度 ≥3，每片有独立负责人？
- [ ] 契约（接口/数据结构）在 fan-out 前冻结？
- [ ] 契约已落盘 `docs/batches/<批次id>/contract.md`，且骨架映射经队长核对零矛盾（两段式冻结）？
- [ ] 同轨串行任务复用同一成员？收口前无单人长尾？
- [ ] 各轨 warmup 已随建队派发？评审依赖绑定单轨而非全局验证门？
- [ ] 每个质量任务带 objective/acceptance（实现/修复另有 inScope/verify）？
- [ ] 评审独立于实现者？
- [ ] 成员规模 ≤ 当前时间窗口预算？

### 反模式（出现即重排 DAG）

- ❌ 巨型任务：单个"负责人"承接多分区实现从头做到尾
- ❌ 假串行：用依赖链模拟本可并行的轨道
- ❌ 队长亲自下场写实现
- ❌ 评审与实现同一人
- ❌ 实现轨闲置干等：verify/review 串行排队而不流水线推进下一片
- ❌ 单人长尾：收口前只剩一名成员干活却拖住全队验证/评审排队（尾部任务拆片并行，或把非关键腿并入集成收口）
- ❌ flaky 尾巴：已知间歇失败用例拖到集成收口才首次暴露（实现阶段并行挂稳定性任务 `--repeat-each≥3`，收口消费其证据）
- ❌ 契约内联全文进任务文本 / 评审从团队状态逐字捞契约（必须读 `docs/batches/<批次id>/contract.md` 文件）
- ❌ 冷启动排队：成员在需求/架构阶段闲置、契约落地后才开始读代码（组队即派 warmup 并行预热，简报喂给架构师）
- ❌ 评审等全局门：review 依赖全量验证完成才开工（应绑定对应轨道即完即评，评审段与尾部实现并行）

## 多智能体团队并发预算（AgentTeams）

额度按模型组**独立计算**（Innostar 网关，超限自动排队不拒绝）：
- `glm-5.3-flash`：白天(07-19) 30 / 夜间(19-07) 40
- `glm-5.3`：白天 8 / 夜间 20

队长组队时**按当前时间窗口动态定规模**，不使用固定小团队默认值（额度是天花板不是目标：先按「标准组织架构与分工」模板定角色，再校验窗口上限）：
- 白天混编上限：flash ≤30 且 glm-5.3 ≤8（合计 ≤38）
- 夜间混编上限：flash ≤40 且 glm-5.3 ≤20（合计 ≤60）
- 插件配置 `maxMembers: 60` 只是绝对天花板（取夜间最大值）；实际规模由队长按窗口与任务粒度决定
- token 消耗不设限（用户授权）；时间最少原则优先，在质量取"可核查"的合理值

## 组队启动方式（AgentTeams）

- **默认由对话直接启动**：队长建队一律用 `approval="automatic"`——成员随建随开工，无需用户在面板点审批（用户长期指令）
- 仅当用户明确要求"先出计划暂存评审 / 让我先看看分工"时才用 `approval="required"`，并在计划提交后停住等审批
- 建队分工必须套用「标准组织架构与分工」：按角色模板 + 扇出/扇入 DAG 一次成型，**禁止把多轨任务编排成单负责人串行**
- 门禁与质量契约规则不变：修复类任务仍需 acceptance/verify 与回归；团队面板仍可实时围观与插话

## 自动启用策略（无需显式调用 AgentTeams）

用户授权：**队长根据任务规模自行决定是否组队**，不要求显式 `/agent-teams` 调用。接到任务后先做规模评估：

满足以下**任一条**即自动组队（`approval="automatic"`，并在回复首行注明"已自动启用 AgentTeams：<原因>"）：
- **多维并行**：任务天然需要 ≥3 个互不依赖的工作流（多维审查、多竞品调研、按模块/所有权分区的实现或修复）
- **体量预估**：预计改动或检查 ≥8 个文件，或可拆出 ≥5 个独立子任务
- **完整质量链**：用户要求走 requirements→实现→验证→评审→集成 的完整门禁流程
- **用户措辞**：出现"组队/团队/并行/多个 agent/分工"等意图词

以下情形**不组队**，由主会话直接处理：单文件修改、单一 bug 修复、问答/简单调研、纯配置或文档微调、探索性原型。

- 规模处于边界时**默认组队**（用户已授权 token 不设限、时间最少原则，宁并行不串行）
- 组队分工与规模按「标准组织架构与分工」+「多智能体团队并发预算」执行：并行轨道各配独立负责人，**并行度 <3 或单负责人串行包揽视为编排失败**；团队运行期间用户插话照常处理

## 禁止行为

- 伪造接口数据、假按钮、无业务逻辑的占位实现冒充完成。
- 为通过测试而直接显示参考截图。
- 修改已冻结的基准/阈值来让失败用例变绿。
- 在用户真实 OneNote 数据上做破坏性操作（本项目的原软件探索只做只读 + 独立 QA 笔记本）。
- 把本可并行的多轨任务编排成单负责人串行执行（反模式清单见「标准组织架构与分工」）。
